Writing a course

From the first clone to your work being on the site. In the examples the course is rl; use your own course's short name, the one in its address.

What you work with

The educator kit is a public repository: {{ kit }}{% if kit_version %} (version {{ kit_version.number }}, {{ kit_version.date|date:"j F Y" }}){% endif %}. It holds the instructions your AI assistant follows, the format of every content file, and three small tools. It holds no course.

Your course comes from this site. You download its files, put them into your copy of the kit, work on them, and hand the result back here. That hand-in is the only upload there is.

Small things can be done on the site itself. On any page of your course press Edit, or open Edit on the site from Educators: lecture notes, labs, homework, guides and the cheat sheet have a form with a preview, and every other file can be changed as text. A save passes the same check as a hand-in and is on the site at once. It also means your copy in the kit is behind: download the course files again before your next hand-in, as described under If the site says the course has changed.

Git is used locally. You will meet git commit and git stash below. Neither sends anything anywhere: a commit is git remembering a version in your own copy, on your computer. It is there so that git diff can show exactly what changed, and so that your work can be put on top of someone else's when the course has moved on. Nothing you write is ever pushed to the kit's repository.

You need git, uv (it runs the tools and fetches what they need), and an AI assistant that can read and write files on your computer. Never used a terminal? The kit's own README starts from there: how to install the two programs, where to type the commands, and what to do when one of them complains.

Once: set up

  1. Clone the kit and switch pushing off, so that your course can never end up in a public place by accident: 
    git clone {{ kit }}.git
cd dsai-educator-kit
git remote set-url --push origin no-pushing
  2. Download your course. On Educators, on your course's card or on its own page, press Download the course files. You get rl.zip: the course exactly as the site has it.
  3. Unpack it into the kit. 
    uv run tools/unpack.py ~/Downloads/rl.zip
    The course is now in courses/rl/, and that state is committed in your copy. That commit is your starting point: from here on, git diff shows exactly what you have added.
  4. Add the material. Put the lecture slides, labs, homework and past papers into courses/rl/source/ (lectures/, labs/, homework/, exams/). Git ignores that folder and the tools never pack it. It belongs to the lecturers and stays on your computer.

{% icon "info" %}Important: material from an earlier year goes in its own folder.

Last year's slides, homework and past papers go in a folder named after that year, courses/rl/source/2025-26/, never mixed in with this year's. That folder is how your assistant knows. It writes the material up as that year's, says so in the text, and does not pass off last year's dates, exam format or coursework as the current ones.

Every time: write, check, hand in

  1. Update the kit. git pull brings the latest instructions and format. It never changes your course. You are told on the Educators page, and by e-mail, when there is a new version.
  2. Let your assistant write. Open the kit's folder in it and say: 
    Update the CMS for this course: rl
    It reads AGENTS.md, learns the format from docs/, finds what in source/ is not written up yet, writes it and checks its own work. For one piece at a time: Update the CMS for this course: rl. Only lecture 3. In Claude Code the same thing is /update-cms rl.
  3. Check what it wrote. This part is yours, and it is why the role exists. Read the notes against the slides; work a few cards and one solution by hand. git diff shows every line that is new.
  4. Pack it. 
    uv run tools/pack.py rl
    It checks the course and writes one file, out/rl-<date>-<time>.zip: your course.yaml and content/, nothing from source/.
  5. Hand it in. On Educators, open your course, choose that zip and press Hand in. The site checks it in full. If it passes it is live at once and appears in the list of what was added.
  6. Note it down, on your computer. Your copy and the site now agree, so tell git that this is your new starting point. This uploads nothing; it is a bookmark in your own copy, so that the next git diff shows only what you do from here on: 
    git add -A courses/rl
git commit -m "rl: handed in"

What a hand-in may do

Add, change and remove. The course is yours to write: a new lecture, more cards, a corrected answer, a deck taken apart and put together better.

Removing has to be meant. A hand-in that removes or rewrites anything is first shown back to you: which files, which lines, which ids. It is taken in when you tick It may change and remove what is there. That is there to catch a slip, such as an assistant tidying up where it should not have. Mind the ids above all: each card, question, formula and term has one, and what students have marked is stored under it. Correct an item in place and keep its id; an id that disappears takes their progress on it along.

Nothing is lost. The site keeps the whole course as it stood after every hand-in and every sitting of edits. History, in the editor, lists them: open a step to see what it changed, line by line, to bring that version of the course back, or to find an earlier version of one file and put it back. On Educators, each step also has Download the course as it was after this step, and your own newest hand-in can simply be taken back there.

Not what is the owner's. In course.yaml the topics and the description are yours. Title, code, year and whether the course is open are not, and a topic's id stays as it is.

If the site says the course has changed

Another educator of your course handed something in, someone (you included) edited the course on the site, or the owner published a change, after you took your copy. Taking your zip in would undo their work, so it is refused. Put your work on top of the latest version:

git stash                              # set your work aside
# download the course files again, on Educators
uv run tools/unpack.py ~/Downloads/rl.zip   # bring in the site's version
git stash pop                          # put your work back on top
uv run tools/pack.py rl                # check and pack again

Usually git fits the two together by itself. Where both changed the same place it marks the file: both versions are in it between <<<<<<< and >>>>>>>. Decide what stays and delete the markers, or tell your assistant: Resolve the merge conflicts in courses/rl. Keep what the site has unless my change replaces it. Then hand in the new zip.

What never leaves your computer

Anything under source/, and scans, photos or copies of slides and papers anywhere. Write your own summary; draw your own figure. Do not push your copy of the kit anywhere public, and do not fork the kit publicly with your course in it.
